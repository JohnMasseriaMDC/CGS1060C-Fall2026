Computer software

02The layers between you and the hardware

The organizing idea

Software splits into two branches. System software runs the machine. Application software is what you actually use. The operating system is the bridge between the physical hardware and your applications — which is why you can use Excel without knowing whether there's an Intel, AMD, or Snapdragon chip underneath.

LayerWhat lives there
YouKeyboard, mouse, touch, voice
Application softwareWord, Excel, Teams, Chrome
UtilitiesSmall tools bundled with the OS — copy, search, disk cleanup
Operating systemWindows, macOS, Linux, Chrome OS, iOS, Android
DriversTranslators that let the OS talk to a specific printer, camera, or gadget
HardwareCPU, RAM, storage, screen, ports

The operating systems, and who's related to whom

OSMakerLineage
Windows 11MicrosoftIts own
macOSAppleDerived from Unix
LinuxOpen source communityUnix-like
Chrome OSGoogleBuilt on the Linux kernel
AndroidGoogleBuilt on the Linux kernel
iOS / iPadOSAppleShares macOS's Unix roots

Unix was created at Bell Laboratories for minicomputers. Because macOS and Linux both descend from it, the command-line commands are nearly identical — learn one and you can work on the other. The kernel is the core of an operating system, the part that actually manages hardware.

Worth noticing how much Linux you already use without knowing it: an Android phone, a Chromebook, a Samsung tablet, an Amazon Fire tablet or Kindle, most web servers you visit, and the world's top supercomputers.

Drivers

A driver is the software that lets your operating system talk to a particular piece of hardware. Most happen invisibly now — Windows ships with printer drivers or fetches them automatically. You notice drivers only when one is missing: I plugged a small radio device into my Chromebook and it worked immediately, plugged the same device into my Mac and nothing happened, and installing a driver fixed it.

Local applications vs. web applications

Word exists as an installed program and as a web app in your browser. The web version is always the latest version, needs no installation, and never needs updating. The installed version is still somewhat more capable, though the gap keeps narrowing.

For organizations, the web model solves a real problem: when software is installed on hundreds of machines, every update and every rollback is a project. When it's a website, you change it once.

  • Software doesn't come on CDs or DVDs. It comes from app stores and websites.
  • The book says Linux runs most video games. PlayStation and Xbox don't — but the Steam Deck does, and so does every Chromebook.
Computer software

03You don't own software — you license it

The core point

When you "buy" software you are buying a right to use it under conditions someone else sets. The agreement is called the EULA — End User License Agreement — and it is a real legal contract, even though nobody reads it.

Same as a movie. Buying a DVD never gave you the right to copy it and hand copies to friends.

ModelHow it works
Perpetual licensePay once, use that version forever. Updates often cost extra. Increasingly rare.
SubscriptionPay monthly or yearly, per user. Stop paying and you lose access. Microsoft 365 and Adobe work this way.
Open sourceSource code is public and modifiable — but it still carries a license, and the terms vary enormously. Linux, Firefox, LibreOffice.

Companies prefer subscriptions because recurring revenue is predictable. There's a defensible reason too: all software has bugs, so it needs continuous fixing, and continuous work needs continuous funding.

Licenses can change — the Java story

Java is software that lets programs written in the Java language run on any machine. A Java program compiles to bytecode, and the Java Virtual Machine on your computer translates that bytecode into instructions your specific chip understands. Write once, run anywhere.

Java came from Sun Microsystems and was free. Sun was bought by Oracle, and Oracle changed the licensing. Companies now get audited, discover they're running unlicensed copies, and receive bills in the millions. Java is the standard example of why "free today" is not "free forever."

Installing software safely

  • Use official sources — the Microsoft Store, Mac App Store, Google Play, the developer's own site, or your school's software page. Apple and Google screen their stores for malware and can disable an app remotely if they find it.
  • Never install "free" copies of paid software. It's piracy, and whoever cracked it had a motive. Pirated installers are one of the most reliable sources of malware.
  • Never act on a pop-up telling you to download something. That's the attack, not a warning about one. Close the browser.
  • Watch the extra checkboxes. Even reputable download sites bundle additional software you didn't ask for.
  • Be suspicious when an installer demands administrator rights. Sometimes legitimate, always worth a second thought.

Why RAM matters most: the potato bag

Twenty pounds of potatoes and a ten-pound bag means you're constantly taking potatoes in and out. That's what your computer does when it runs out of RAM — it shuffles data between memory and storage, a process called swapping, and when it gets bad enough it's called thrashing. Everything crawls.

Every browser tab you open consumes memory. Running out of storage is annoying; running out of RAM makes the machine unusable. And remember from last week — there's a global RAM shortage driven by AI data centers, so prices aren't falling soon. Buy more than you need today.

05Databases, starting from spreadsheets

Learn this mapping and most of the vocabulary follows
In a spreadsheetIn a database
WorksheetTable
RowRecord
ColumnField
FilterQuery
Typing data inForm
Printing it outReport

The data hierarchy builds upward: a character is one letter or digit; several characters make a field; several fields make a record; many records make a table; tables live in files; and a database is made up of those files.

You're already in dozens of databases

Your student record at the college, keyed by your student ID, holding your courses, grades, and financial aid. Your doctor's patient portal. Your lab results. Your bank balance. The Contacts app on your phone is a database. Amazon's record of every order placed today.

Why not just use a spreadsheet?

Modern spreadsheets can be shared and edited simultaneously, so that's no longer the reason. The real reasons are:

  • No audit trail. If a phone number changes in a shared spreadsheet, there's no record of who changed it or when.
  • No access control. You can't let someone see most of a sheet but not the salary column.
  • No protection against duplication. Which leads to the central principle below.
Store each fact once

If Maria Lopez's phone number is written in twenty appointment rows and she changes her number, you must find and fix twenty places. Miss one and your data is now wrong.

A relational database stores the phone number once, in the client record, and everywhere else points at it. Change it in one place and every reference is correct.

Data types are guardrails

When you design a table you choose a type for each field, and the type restricts what can be stored:

TypeGuardrail
Short textAlmost none — letters, digits, symbols, emoji all accepted
Date/TimeMust be a real date. Stops someone typing "next Tuesday." Stored as a number internally, exactly like Excel dates.
NumberDigits only. Stops the letter O being typed for a zero.
Yes/NoOnly two possible values

Choosing types well is most of what database design means. A phone number stored as free text will eventually contain garbage.

Databases

06Keys and relationships

These are called relational databases because data in one table relates to data in another. The model was designed by Edgar F. Codd at IBM in 1970 and is still how most of the world's important data is stored.

Primary key

  • Unique for every record in its table
  • Never null
  • Should never change

Your student ID is a primary key. So is an employee ID. Databases build an index on the primary key, which is why a system with a million client records can find one instantly instead of reading all million.

Textbook correction: never use an SSN as a primary key

The book offers Social Security number as an example of a good primary key. It is a bad one. An SSN is PII — personally identifiable information — and a primary key gets copied into every related table, spread through every query, and seen by everyone with access. That's the opposite of what you want for sensitive data. Use a meaningless generated ID instead.

Foreign key

A foreign key is a field in one table that points at the primary key of another. In the spa example, the appointments table carries a client_id and a service_id; each links the appointment to exactly one client and one service.

That's how the pointer works in practice: appointment 5001 holds client ID → Maria Lopez, and service ID S3 → Massage, $95. The price lives once, in the services table.

Null

Null is not zero. Zero is a value. Null means no value is stored here — we don't know Maria's phone number, as opposed to her phone number being 0. If a field must always be filled, mark it required and the database will refuse records without it.

Relationship types

TypeExample
One-to-manyOne client has many appointments. By far the most common.
Many-to-oneThe same relationship seen from the other side — many employees report to one manager.
One-to-oneOne employee has one parking permit.
Many-to-manyStudents and courses — each student takes many courses, each course has many students.
Correction from class

I described "one employee has one manager" as one-to-one. It isn't — that's many-to-one, because one manager has many employees. The parking permit is the genuine one-to-one.

Databases

07Data integrity

Data integrity asks: can I trust this data? Five dimensions:

DimensionQuestion
AccuracyIs the birthdate actually right?
TimelinessIs it current, or three years stale?
CompletenessDoes the address have all its parts?
ConsistencyIs Florida stored as FL everywhere, or sometimes "Fla." or "Florida"?
ComplianceIs protected data restricted to the people entitled to see it?

Consistency is enforced at two levels, and good systems use both. In the interface: a drop-down list of states instead of a free-text box, so the wrong value can't be typed. In the database: rules defining which values are permitted, so anything that slips past the interface is rejected anyway.

Compliance is why access control exists at the field level, not just the table level. A professor looking up a student record needs their email; they have no business need for the student's Social Security number.

DBMS — the five parts

A Database Management System is the software running the database. It provides:

  1. The engine that stores and retrieves data
  2. Data definition — defining tables, fields, and types
  3. Data manipulation — add, change, delete, query
  4. An administrative interface for forms and views
  5. Administration — backup, recovery, and security
Databases

08Queries, and the ACID guarantees

A SELECT statement

SQL is the language used to ask a database questions. The structure is readable even if you've never written one:

SELECT first_name, phone
FROM clients
WHERE city = 'Doral'
ORDER BY first_name;
  • SELECT — which fields you want back
  • FROM — which table
  • WHERE — the filter
  • ORDER BY — how to sort the result

Change the WHERE clause and you ask a different question: every client whose last visit was more than 90 days ago, for instance.

ACID — the four guarantees that make databases trustworthy

A — Atomicity. A transaction happens completely or not at all. Move $100 from savings to checking: the system subtracts $100 from savings, then adds $100 to checking. If the power fails between those two steps, your $100 has vanished. Atomicity means the database notices the incomplete transaction on restart and rolls it back entirely.

C — Consistency. The database's rules always hold. If phone number is required, a record without one is rejected rather than quietly stored broken.

I — Isolation. Simultaneous transactions don't corrupt each other. If you and your spouse both withdraw at the same instant, both could read a $500 balance, both subtract $100, and both write $400 — the bank loses $100. Isolation makes the second transaction wait until the first commits.

D — Durability. Once a transaction commits, it survives a crash or power loss. The database writes to an audit trail at the moment of commit, so on restart it can tell which transactions finished and which must be undone.

Two corrections

Textbook: NoSQL is not a product. It's a category, and it stands for "not only SQL." The products are MongoDB, DynamoDB, Redis, and Cassandra.

From class: I kept saying "Progress" when I meant PostgreSQL, usually shortened to Postgres. That's the open-source relational database Amazon offers cheaply through AWS, because unlike Oracle or SQL Server there's no license fee to pass on. Progress is an unrelated company — search for Postgres.

Kinds of NoSQL

  • Document stores (MongoDB, Cassandra) hold documents, usually in JSON — JavaScript Object Notation, a compact text format of name/value pairs: {"name": "John", "age": 30, "city": "New York"}.
  • Key-value stores (Redis) take a unique key and hand back a value. A shopping cart works this way: your session ID is the key, the list of items is the value.
  • Graph databases model relationships between things — who knows whom, what connects to what.

Good rule of thumb: not for your bank account. Excellent for shopping carts, website sessions, and Internet-of-Things sensors streaming a reading every hour.

Warehouses, marts, and mining

  • A data warehouse is a central store of historical data for a whole organization.
  • A data mart is a smaller slice of one, serving a single department.
  • Data mining is searching that data for patterns worth knowing.
The ironic part

A transactional database works hard to eliminate duplicated data. A data warehouse deliberately puts the duplication back — a process called denormalization.

Why: a normalized database is optimized for fast, safe updates. A warehouse is optimized for fast analytical queries over enormous history, and duplicating data means those queries don't have to join a dozen tables. You trade storage for speed, which is exactly the right trade when you have hundreds of terabytes and nobody is updating them.

Classifying data

PairDistinction
Qualitative / QuantitativeHow good was it? (survey ratings) vs. how many / how long (numbers)
Discrete / ContinuousWhole numbers — you can't serve 14½ clients — vs. measurements like temperature or weight
Nominal / OrdinalCategories with no order (types of service) vs. categories with order (poor, fair, good, excellent)
Structured / UnstructuredDatabase rows and columns vs. photos, video, audio, free text

Note: some publisher materials reverse nominal and ordinal. The definitions above are correct.

Where data comes from

  • First-party — you collected it, from your own customers.
  • Second-party — another organization's first-party data, shared or sold to you directly. A spa buying a partner gym's member list.
  • Third-party — bought from data brokers, who aggregate from many sources.
Privacy and aggregation — the subtle problem

Obviously private: name, SSN, email, phone, medical records, account numbers.

The harder problem is that enough individually harmless fields, combined, identify a specific person. Age range, ZIP code, job title, and number of children aren't private individually. Together they may describe exactly one person.

This is why Google won't run an ad targeted too narrowly — if your filters shrink the audience below a threshold, the ad is blocked. Otherwise, one click tells you precisely who that person is, and they never agreed to that.

Note that this is a privacy problem, not a security one. The data wasn't stolen. It was used in a way the person didn't expect.

Cleaning data ("wrangling")

Real data arrives messy. Before analyzing anything you:

  • Deduplicate — merge the two Maria Lopez records
  • Standardize — every "Florida," "Fla.," and "FL" becomes FL
  • Format consistently — one date format, one currency format
  • Fix types — "$1.95" stored as text can't be summed; store 1.95 as a number
  • Trim — strip stray spaces, fix capitalization

Small data: a spreadsheet handles it. Millions of rows: use a database. This is also where last week's Excel text functions earn their keep.

Data analytics

11Choosing charts, and not misleading people

ChartUse when
LineSomething changes over time. Time on the x-axis.
BarComparing separate groups — regions, age brackets, products
ScatterLooking for a relationship between two measurements — square footage vs. sale price
PieParts of a whole adding to 100%, and only with a handful of slices

A pie chart with a hundred slices communicates nothing. If you have a long tail, group it into an "Other" slice.

Correlation is not causation

Ice cream sales and sunburns rise together. Ice cream doesn't cause sunburn — summer causes both.

A real published study found that countries consuming more chocolate win more Nobel Prizes. Chocolate doesn't make you smarter. Wealthy countries have both more chocolate and better-funded research.

When two things move together, always ask whether something else is driving both.

Three ways charts mislead

Truncated axis. Start a bar chart's y-axis at 48% instead of 0 and a two-point difference looks like a landslide. Set the floor to zero and it nearly disappears. Sometimes scaling is legitimate — when a small difference genuinely matters — but you must be able to justify it.

Cherry-picking. Discarding results you don't like. Decide your rules for collecting and excluding data before you see the results.

Too many categories. A chart nobody can read isn't informative, however accurate.

How companies actually use this

Web analytics is one of the biggest applications. A company builds a funnel: everyone lands on the homepage, fewer reach a product page, fewer add to cart, fewer check out. The interesting question is where people drop off and why. Those answers come from web logs — which are unstructured data, loaded into a data mart and queried.

Your textbook frames it as data + organizational knowledge = problem solved. Reasonable, with one addition: data + knowledge + the right tool. Data alone tells you nothing, and neither does a tool without someone who understands the business.
